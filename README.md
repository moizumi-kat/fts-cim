## 2. bin/scan.py — 呼び出し関係の走査

    python3 -I bin/scan.py <UTF-8にそろえたソースのフォルダ> work_map.json

村上様のご指摘を受けて5回直している。**抜けはすべて「呼び出しの書き方」の見落とし**で、
現行側の欠落ではなかった。数えている形は次のとおり。

| 形 | 例 | 気づいた経緯 |
|---|---|---|
| CL の CALL | `CALL A10010PO,(?WSNAME)` | 最初から |
| COBOL の CALL（引用符つき） | `CALL "A10040PO"` | 村上様ご指摘（10-28） |
| PROGRAM-ID で名前解決 | `BUHINM2S.COB` の PROGRAM-ID は `BUHINM2O` | 村上様ご指摘（10-29）。192本が該当 |
| SBMJOB の PGM- | `SBMJOB …,PGM-CA1Z1100,…` | 自力（10-29）。これが最大の抜けだった |
| **COPY … OF FZSLIB** | `COPY JYUSYORI OF FZSLIB.` | 村上様ご指摘（11-03） |
| **CALL が行頭でない** | `THEN CALL CD4X0121` | 同上 |
| **CL 名をそのまま書く** | `SUIHYCL1 YY-?YEAR,MM-?TUKI` | 同上 |

XFDLIB（ファイル記述 609種）と XMDLIB（画面定義 352種）の COPY は、プログラムの
呼び出しではないので依存に数えない。

## 2.4 呼び出しの辿り方（村上様ご説明 2026-10-29／実測で確認済み）

村上様より、呼び出しの辿り方について2点のご説明をいただいた（2026-10-29）。
**どちらも `bin/scan.py` に入っている。** 実測値を下に残す（`python3 bin/scan.py <ソース置き場> out.json`）。

### (1) CLとCOBOLの呼ばれる4パターン

4パターンすべて拾えている。のべ回数は実測（ソース1,415本）。

| パターン | 実測 | 拾い方 |
|---|---|---|
| CL ⇒ COBOL | **1,753回** | `CALL 名前`／`SBMJOB PGM-名前`／**CLに名前をそのまま書く形**（`CALL` を書かない） |
| CL ⇒ CL | **297回** | 同上 |
| COBOL ⇒ COBOL | **41回** | `CALL "名前"`（引用符つき） |
| COBOL ⇒ CL | **7回** | 同上 |

**5つめの形もある。** `COBOL ⊂ COBOL（COPY）` **8回**＝`COPY … OF FZSLIB` で
**プログラム本体を取り込む**形（`CALL` ではないので呼び出しに見えない）。
全ソースで1本だけ（`CHK5S010.CL → CALL NPJYU5CS → COPY … OF FZSLIB`）。
`XFDLIB`（記述）・`XMDLIB`（画面）の COPY は依存に数えない。

### (2) ソース末尾「S」は実行形式では「O」

ご指摘のとおり。**`PROGRAM-ID.` の行に実行形式名が書かれており、CLはその名前で呼ぶ**ので、
`scan.py` は**末尾の文字で読み替えるのではなく、全COBOLの `PROGRAM-ID` を読んで
「実行形式名 → ソース名」の表を作り**、CLの呼び出しをその表で引いている（`jikkou`）。

実測（2026-11-11）

| | 本数 |
|---|---|
| `PROGRAM-ID` がファイル名と違う COBOL | **190本** |
| うち ソース末尾S → 実行形式末尾O | **188本** |
| **それ以外の読み替え** | **2本** |

**「S→O」だけでは2本取りこぼす。** 実例

    BANKIN1O  ← BANKIN1S.COB     （S→O。188本がこの形）
    DATECHKO  ← DATECHKP.COB     ← **P→O**。末尾の規則では拾えない
    TUKICHKO  ← TUKICHKP.COB     ← 同じ

この読み替えで辿れている呼び出しは**のべ187回**。読み替えが無ければ、この分だけ
「呼ばれているのにソースが無い」と誤判定していた（`doc/2026-11-04 依頼…811本.txt` の
「２．末尾がOのもの 223本」は、この読み替えを**効かせたうえで**なお見つからない分）。

## 2.43 索引（キー）は FILE-CONTROL に書いてある ＝ XFDLIB は要らない

子6本が `COPY xxx OF XFDLIB` で取り込む記述体21本は未入手だが、
**索引（どの項目をキーにしているか）は COBOL の FILE-CONTROL に書いてある。**

    SELECT 鑑ファイル ASSIGN TO DA-01-VI-AJBGFL1
           ORGANIZATION IS INDEXED
           RECORD KEY   IS AJBG-MITUNO          ← これ
           ACCESS MODE  IS DYNAMIC
           FILE STATUS  IS AJBG-STSCD

名前の対応も素直。**`AWKG-MITUNO` の「-」より後ろが表の列名**（実測）。
論理ファイル `AWKGFL1` → 物理表 `AWKGFP`。

`bin/gen_fairu.py` がこれを読んで `fairu_<プログラム>.py` を起こす。
A10040PO は **18本すべて**表とキーに辿れた。

ひとつだけ集団項目があった。`ASUNML1` のキー `ASUN-SUNPO` は表に無く、
**巾・高さ・奥行（WIDTH＋HIGH＋DEPTH）をまとめた集団項目**だった
（4478-4480行の注記に `MOVE AWKM-DW/DH/DD TO ASUN-WIDTH/HIGH/DEPTH`、
4348行に `MOVE HIGH-VALUE TO ASUN-SUNPO`）。生成器に根拠つきで持たせてある。

→ **XFDLIB21本のお願いは、さらに優先度が下がった**（レコードの並びはレコード
　 リストから、索引は FILE-CONTROL から取れている）。

### 型の規則（既存32表の実測に合わせたもの）

| PIC | SQL Server | 根拠 |
|---|---|---|
| `X(n)` | `char(n)` | 48件一致 |
| `N(n)` | `nchar(n)` | 13件一致 |

| `S9(a)V9(b)` / `9(a)V9(b)` | `numeric(a+b,b)` | 小数点があれば符号つきでも numeric。2件 |

### 繰返し（OCCURS）は**メモリ上の並びのまま**

集団項目に `OCCURS 50`、その中に KAISHI と OWARI があるなら

    KAISHI_1, OWARI__1, KAISHI_2, OWARI__2, …

と**交互**に並ぶ（KAISHI を50個並べてから OWARI ではない）。現行ファイルの
バイト位置と合わせるため、ここは崩してはいけない。NOKIB4SF で実測。

### レコードリストの OCR 誤り — 直したのは3件だけ

レコードリストは PDF から起こしたもので、B↔E・I↔1 の取りちがえがある。
**根拠を示せるものだけ**直し、根拠が無いものはそのまま出す（`recdef.NAOSHI`）。

| 表 | リストの字 | 直した字 | 根拠 |
|---|---|---|---|
| NIPSYOFP | BGKOSN | EGKOSN | この表の項目はすべて EG… で始まる。BG… は1つだけ |
| NIPSYOFP | BGYOHK | EGYOHK | 同上 |
| NOKIB4SF | YOBIHI | YOBIH1 | 直後に YOBIH2（予備日付２）が並ぶ。村上様の定義体 NOKIKFFP.sql にも YOBIH1 が実在 |

### ⚑ 方針の決定（2026-11-11 茂泉様ご決定）

**「1:1で写し切ってから、統合は後で載せる」**

Dropbox の「FTS-CIM 新システム設計書.xlsx」には、799ファイルを **204表に統合**して
`T_案件` のような新しい名前を付ける設計がある。これは**第2段**とし、まず現行を
**489表 1:1（名前も列名も現行のまま）で写し切る**。

理由：いま点検が全部通っているのは「現行と同じ名前・同じ桁だから、現行の出力と
全項目つき合わせられる」から。先に統合すると、数字が合わないときに**移植ミスか
統合の設計差か切り分けられなくなる**。統合は1:1の上にビューや対応表として後から
載せられる。

→ 村上様へは「設計書の204表統合は1:1移植が通ったあとの第2段としてよいか」を
　 確認中。返事待ちの間も1:1で進める（手は止まらない）。

- **⚠ 表の数は 204 → 403 → 489 と2回訂正している。最新は 489。**
  - 204 … 呼び出しの取りこぼしを直す前（到達COBOL 379本）の数。
  - 403 … 取りこぼしを直して到達COBOL が 802本になったあと、こちらで405工程から数えた数。
